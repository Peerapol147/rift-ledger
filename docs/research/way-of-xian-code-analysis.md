# วิเคราะห์ระบบ Way of Xian จากโค้ด — 13 พฤศจิกายน 2026

## ขอบเขตและหลักฐาน

วิเคราะห์จาก HAR ที่เจ้าของส่ง ไม่ได้เดาจากภาพหน้าจอ HAR มี 683 entries ขนาดแตกไฟล์ 194,769,513 bytes ดึง response ประเภท JavaScript/JSON/HTML/text ที่มีเนื้อหาได้ 329 ชุดไม่ซ้ำกัน (นับตาม SHA-256 ของเนื้อหา ไม่ใช่จำนวนระบบเกม) มีซอร์สอ่านได้และแยกโมดูล จึงไม่ต้องถอดโค้ด minified เพื่ออ่านแกนหลัก

ต้นฉบับเก็บเฉพาะใน workspace ที่ `/workspace/scratch/xian-research/code/`; manifest จับคู่ชื่อไฟล์กับ URL path อยู่ข้างกัน ไม่ได้นำ HAR, header, cookie หรือข้อมูลบัญชีเข้า repository รายงานนี้เป็นบทวิเคราะห์ ไม่ได้คัดลอกเกมมาใช้

การอ้างอิงด้านล่างใช้ path เดิมของเว็บและเลขบรรทัดใน response ที่เก็บมา เวอร์ชันนี้เป็น snapshot จาก HAR ไม่รับรองว่าเหมือนเว็บล่าสุด โค้ดเซิร์ฟเวอร์ Cloudflare Worker ไม่ได้อยู่ใน HAR และยังไม่ได้ตรวจทุกเรื่องย่อย/ทุกฉาก/ทุกสูตร จัดผลเป็น:

- **ตรวจโค้ด:** อ่าน implementation ของกลไกที่ระบุ
- **ทดลอง:** รันโมดูลสูตรต่อสู้แบบแยก ไม่มีการเรียก API หรือใช้บัญชี
- **พบโมดูล:** ยืนยันโครงสร้างระบบ แต่ยังไม่วิเคราะห์สมดุลและทุกทางเดิน

## 1. แกนของเกม: จำลองชีวิตรายเดือนที่มีการตัดสินใจคั่น

**ตรวจโค้ด:** `src/sim.js:1628,2059`, `src/ui.js:158,6030`

วงจรหลักคือสร้างชีวิต → เลือกแนวทาง/กิจกรรม → เดือนเดิน → โลกและตัวละครเปลี่ยน → เหตุการณ์ค้างรอคำตอบ → ผลลัพธ์แก้สถานะ → เดือนถัดไป เกมไม่ใช่เพียงสุ่มข้อความแล้วบวกค่าพลัง: มีสถานะความสัมพันธ์ ตำแหน่ง การเดินทาง ภารกิจ และเงื่อนไขเรื่องราวที่ดำเนินต่อ

- หน่วยข้อมูลอายุคือ `ageMonths`; `monthStep` หยุดเมื่อมี `pending` หรือชีวิตสิ้นสุด
- เวลาพื้นฐานของ UI คือ 5,000 ms ต่อเดือน มีปัจจัยความเร็ว/การเดินทาง/ฉากเข้ามาปรับ ไม่ใช่รับประกันทุกเดือนจะใช้ 5 วินาทีจริง
- ความเร็วที่เลือกได้คือ 1, 2, 3, 5, 10
- เมนู การ์ดบุคคล กระเป๋าและวิชา รวมถึงฉากที่ยังเล่นอยู่ สามารถพักนาฬิกาได้ ทำให้ผู้เล่นอ่านและเตรียมตัวก่อนเดินต่อ
- RNG ใช้ state แบบ 32-bit (`rng.js`) เพื่อให้การจำลองดำเนินตามลำดับสุ่มที่บันทึกไว้ ไม่ควรสรุปว่าทุกภาพ/ทุกระบบออนไลน์ deterministic ทั้งหมด

**นำมาใช้กับ Rift Ledger:** ทำให้นาฬิกา เหตุการณ์ และสถานะ modal ใช้กฎการพักเดียวกัน แยก “เวลาเดิน” ออกจาก “อนุญาตเลือกแทน”

## 2. การสร้างตัวละครเป็นการแลกทรัพยากรเริ่มต้น

ตัวอย่าง: ราชวงศ์ 5 แต้ม, รากสวรรค์ 8, รากธาตุพิเศษ 10, เส้นเอ็นมังกร 10, ดาวนำชะตา 10 ดังนั้นเลือกจุดแข็งสูงสุดทุกด้านพร้อมกันไม่ได้ มีการตรวจจำนวนธาตุไม่ซ้ำและชนิดธาตุที่ถูกต้อง และมีโหมดให้ชะตาสุ่มองค์ประกอบตั้งต้น

**สำหรับเรา:** ภูมิหลัง/ความถนัด/ข้อเสียสามารถใช้แต้มร่วมกันได้ แต่ควรคงทางเล่นแบบสุ่มและเส้นทางคนไม่ตื่นพลัง

## 3. เติบโตหลายเส้นทาง ไม่บังคับทุกคนขึ้นบันไดเดียวกัน

**ตรวจโค้ด:** `src/data.js:134,305,323,356`, `src/sim.js:2059,17863`

มีทั้งสายผู้ฝึกตน สายยุทธ และชีวิตทางสังคม/ราชสำนัก กฎไม่ใช่แค่เปิดทุกระบบพร้อมกัน เช่นผู้ฝึกตนที่ยังมีตำแหน่งราชการหรือทหารถูกนำออกจากบทบาทนั้นในเดือนจำลอง

ตารางผู้ฝึกตนมี 9 realm รวมคนธรรมดา: คนธรรมดา → หลอมปราณ → สร้างฐาน → แก่นทอง → วิญญาณก่อเกิด → แปลงวิญญาณ → ผสานความว่าง → ข้ามทัณฑ์สวรรค์ → บรรลุเซียน ระดับมีทั้งชั้นย่อยและอายุขัยพื้นฐานของตนเอง ตัวอย่างอายุขัยในตาราง: 75, 100, 180, 300, 600, 1,000, 1,500, 2,200, 10,000 ปี; อายุจริงยังมี modifiers และเส้นทาง compatibility ของเซฟเก่า

Focus หลักให้ตัวคูณ activity/growth/events = 3/1.5/2; Focus รอง = 1.75/1.25/1.4 ตัวเลขนี้เป็นน้ำหนัก/ตัวคูณในระบบที่เกี่ยวข้อง ไม่ใช่โอกาสเหตุการณ์เป็นเปอร์เซ็นต์โดยตรง

**สำหรับเรา:** แผนรายเดือนควรเปลี่ยนทั้งความก้าวหน้าและชนิดเรื่องที่พบ ทำให้ผู้เล่นเห็นว่าการเลือกแผนกำลังเปลี่ยนชีวิต

## 4. สูตรสะสมพลังมีการลดช่องว่างพรสวรรค์

**ตรวจโค้ด:** `src/sim.js:17863–17896`

เขียนย่อสูตรการได้รับปราณต่อเดือน:

`gain = realm.absorb × 0.5 × (max(0.000001, innate) / 0.5)^0.79 × startAgeMultiplier × methodSpeed × modifiers`

`innate = rootSpeed × (0.5 + purity/100) × talentProduct × (0.8 + relativeMind/250) × (1 + diligence/400)`

modifiers รวมสำนัก/วิชาและเงื่อนไขที่ฟังก์ชันเรียก เช่นอาจารย์ การปลีกวิเวก สัตว์คู่ใจ ดันเจียน สมบัติ และสถานะผิดปกติ บางสถานะทำให้ gain เป็นศูนย์

กำลัง 0.79 ลดช่องว่างของค่า innate: ผู้เก่งกว่าเติบโตเร็วกว่า แต่ไม่ปล่อยผลคูณพรสวรรค์วิ่งเป็นเส้นตรงทั้งหมด คอมเมนต์เรื่อง “เร็วกว่า 13 เท่า” เป็นผลทดลองที่ผู้สร้างระบุ ไม่ใช่ผลที่เราจำลองชีวิตยืนยันรอบนี้

## 5. ทะลวงขั้นเป็นการตัดสินใจเรื่องเวลาและความเสี่ยง

**ตรวจโค้ด:** `src/sim.js:21205–21264`

- เลื่อนชั้นย่อยในฟังก์ชันนี้สำเร็จ 90%; พลาดทำให้ปราณเหลือ 70%
- ทะลวง realm ใช้โอกาสฐานของขั้นถัดไป ปรับด้วยเจตจำนง โชค ยา เต๋า พรสวรรค์ สมาธิ กรรม และสถานะ
- ช้าเกินไปมีโทษตามสัดส่วนอายุขัยที่เหลือ ลดโอกาสได้ถึง 25%
- พลาดสะสมช่วยครั้งต่อไป +3 จุดเปอร์เซ็นต์ต่อครั้ง สูงสุด +15 จุด
- ผลสุดท้ายของโอกาสสำเร็จจำกัดที่ 2%–95%
- คำนวณความเสี่ยงตายแยกจากโอกาสผ่าน ไม่ใช่พลาดทุกครั้งต้องตาย ต้องตามตัวเรียกและเครื่องป้องกันเพื่อประเมินผลสุดท้าย

**สำหรับเรา:** การเลื่อนแรงก์ฮันเตอร์ควรให้เตรียมตัวและเห็นเหตุผลที่ยังไม่พร้อม พร้อมกลไกช่วยหลังพลาด แต่อัตราตาย/เพดานห้ามคัดตัวเลขมาใช้โดยไม่จำลองสมดุลของเรา

## 6. สูตรต่อสู้: ระดับ × วิชา × อุปกรณ์ พร้อมคุณสมบัติแยก

**ตรวจโค้ดและทดลอง:** `src/fight-calc.js:22–206`; ตัวเรียก/การแปลงตัวละครอยู่ `fight-life.js` และ `sim.js`

`base = 100 × 1.7^(level−1) × (1 + 0.3 × stage)` โดย stage อยู่ 0–1

`power = base × (1 + artsContribution) × (1 + gearContribution) × scale`

- พลังจากช่องวิชาหลัก: ต่อสู้ 0.25, วิธีฝึก 0.05, สนับสนุน 0.10; วิชาเคลื่อนที่/ป้องกันส่งผลหลบและลดความเสียหายแยก อย่าอ่านว่า “ทุกวิชาบวก power รวม 50%” ตามคอมเมนต์อย่างเดียว
- ช่องอุปกรณ์: อาวุธ 0.30, เกราะ 0.25, เครื่องประดับ 0.10 สองช่อง, สมบัติ 0.05 รวม 0.80 เมื่อคุณภาพมาตรฐานทุกช่อง = 1
- คุณภาพเมื่อ tier ต่ำกว่าที่ระดับต้องการ: 1 / 0.7 / 0.4 / 0.15; mastery ให้ 0.6–1.0 ก่อนตัวคูณเข้าธาตุและค่าสถานะ
- Body เพิ่ม HP, Luck เพิ่มหลบ, Mind เพิ่มคริติคอลและความแรงคริติคอล, Will เพิ่มสวนกลับและลดโทษใจฝ่อ ไม่ได้ยัดทุก stat ลง power ก้อนเดียว
- ต่อสู้สูงสุด 8 รอบ มีสุ่มผู้เริ่มโจมตีและ form แบบ log-normal ตลอดไฟต์ หากยังยืนทั้งคู่ตัดสินจากสัดส่วน HP ที่เหลือ
- อาวุธมีวงแพ้ทาง long > quick > heavy > long ใช้ edge 0.05 ในตัวคูณโจมตี ไม่ใช่ชนะเพิ่มคงที่ 5 จุดเปอร์เซ็นต์
- `deathOdds` ของโมดูล = clamp(0.05 × foePower/selfPower, 0.03, 0.12) เป็น helper สำหรับแพ้สู้ ไม่ใช่อัตราตายของเหตุการณ์ทุกชนิด

## 7. ดันเจียนเป็นการวางแผนก่อนเข้าและตัดสินใจว่าจะกลับเมื่อไร

**ตรวจโค้ด:** `src/dungeon.js:8–60`

แผนประกอบด้วยระดับ/ความลึก เป้าหมาย ท่าที เกณฑ์ถอนตัว และของที่เตรียม มี 4 watches ต่อเดือนในดันเจียน มีช่วงพักระหว่างรอบ 3 เดือน

| ท่าที | ตัวคูณของ | ตัวคูณ danger | ข้อสังเกต |
|---|---:|---:|---|
| cautious | 0.7 | 0.6 | มีค่าช่วยหลบ/รับมือกับดัก |
| balanced | 1.0 | 1.0 | ค่าปกติ |
| greedy | 1.4 | 1.5 | ได้มากขึ้น เสี่ยงสะสมเร็วขึ้น |

ถอนเมื่อ HP ต่ำกว่า 30/50/70% ตามแผน; ค่าเริ่มต้น 50% danger อยู่ 0–100 และความแข็งของศัตรูใช้ `1 + danger/300` ใน helper ปราณในพื้นที่อยู่ช่วง 1.3–1.8 เท่า

**สำหรับเรา:** ประยุกต์เป็นแผนลงเกตได้ตรงที่สุด: เป้าหมาย/ความเสี่ยง/ของเตรียม/เกณฑ์ถอย และแสดงผลแลกเปลี่ยนก่อนกดเข้า อย่ารับประกันว่า “ตั้งถอยแล้วไม่มีวันตาย” เพราะเหตุการณ์ระหว่างทางยังมีผล

## 8. คราฟต์และยาออกแบบให้มีต้นทุนสะสม

**ตรวจโค้ด:** `src/craft.js:132–165`, `src/pill-resist.js:13–35`

โอกาสคราฟต์ฐานตาม tier คือ `[60,50,40,30,18,8]%` เพดาน `[95,95,90,80,65,45]%` ก่อนข้อยกเว้น ปรับจากวิชา เครื่องมือ เต๋า ธาตุ และ stat เทียบค่ามาตรฐานของตัวละคร ขั้นต่ำทั่วไปในฟังก์ชันคือ 3%; ไม่มีวิชา/เครื่องมือคืน 0 คอมเมนต์บนไฟล์ที่พูดฐาน 25% และ clamp 5–92% ไม่ตรงกับ implementation นี้

ยากลุ่มเดียวกันในหน้าต่างเวลาทำให้ประสิทธิภาพลดแบบ `k^จำนวนครั้ง`: ยาปราณ k=0.6 ภายใน 3 ปี, ยาทะลวง k=0.5 ภายใน 5 ปี, ยาอายุ/หลอมราก k=0.4 ภายใน 10 ปี ยาเกรดสูงที่เข้าเงื่อนไขยกเว้นและยารักษาฉุกเฉินไม่ถูกลงโทษแบบนี้

**สำหรับเรา:** ป้องกันการซื้อยาแล้วข้าม progression ทั้งหมด แต่ต้องอธิบายผลใช้ซ้ำก่อนกดใช้

## 9. โลกและ NPC ไม่ได้หยุดรอผู้เล่น

**ตรวจโค้ด:** `src/growth.js:8–177`, `src/sim.js:2059`

NPC ที่เข้าเงื่อนไขเติบโตมีเส้นทางคำนวณจาก id และเดือนเกิด พรสวรรค์ ความเข้าใจและความขยันกำหนดเวลาเลื่อนขั้น มีโอกาสติดขัด โชคดี บาดเจ็บ หรือหยุดอยู่ที่ขีดจำกัด ข้อมูลเส้นทางคำนวณแล้ว cache ต่อบุคคล มีตัวช่วยยกเพดานจากการช่วยเหลือของผู้เล่น

สำคัญ: `growth.js` เป็นสูตร NPC ไม่ใช่สูตรฝึกของผู้เล่น ตัวละครสำคัญของสำนัก สัตว์ และ cast แบบ fixed บางประเภทถูกยกเว้น อย่าเหมารวมว่า NPC ทุกคนใช้กฎเดียวกัน

**สำหรับเรา:** ให้คู่แข่ง เพื่อน และสมาชิกทีมมีความก้าวหน้า/เหตุการณ์ของตนเอง และให้การช่วยเหลือของผู้เล่นส่งผลย้อนกลับมา

## 10. ความสัมพันธ์และเรื่องยาวมีสถานะคงอยู่

**ตรวจโค้ดโครงสร้างและกฎบางส่วน:** `src/bonds.js:1–17`, `src/stories.js:1–18`

ความสนิททั่วไปมีจุดกั้น 59 ก่อนผ่านบททดสอบความสัมพันธ์ มี tags ของพันธะลึกที่เป็นข้อยกเว้นและความทรงจำร่วม เรื่องยาวเก็บตำแหน่งขั้นปัจจุบัน เวลาที่เริ่ม cast ที่ผูกกับบุคคลจริง และ ending การเดินเรื่องมีเงื่อนไขระยะเวลาระหว่างขั้น เงิน ของ stat ระดับ และความสัมพันธ์

**สำหรับเรา:** เหตุการณ์ช่วยคนไม่ควรจบที่เงิน +10 แต่ควรผูก NPC/ธงเรื่อง/นัดหมายครั้งหน้า เพื่อให้ผู้เล่นจำได้ว่าเคยทำอะไรไว้

## 11. ออโต้เป็นสิทธิ์ที่ผู้เล่นเปิด และแยกเป็นรายระบบ

**ตรวจโค้ด:** `src/ui.js:1817–1822,13571`, `src/auto.js:94–124`

- global fate เปิดเฉพาะเมื่อ localStorage `lifesim.autoFate` เท่ากับ `"1"`; ไม่มีค่า = ปิด
- ตัวเลือกออโต้ย่อยไม่มีข้อมูล = `{on:false}`
- เหตุการณ์ `epic`/`legendary` หยุดรอ เว้นผู้เล่นเปิด rare auto
- หน่วงการเลือกแทนค่าเริ่มต้น 5 วินาที ตั้งได้ 1–30 วินาที
- ประมูลมีงบรวมตามเงินตั้งต้น 10%,25%,50%; เดินทางไกลมีสิทธิ์ยืนยันอัตโนมัติแยก
- `autoChoose` มีหลายกฎเฉพาะเรื่อง ไม่ใช่เลือกข้อแรกทุกครั้ง จึงไม่ควรยกสูตรคะแนนเดียวมาอธิบายทั้งหมด

**ตรงกับคำถาม Default ของเจ้าของ:** ต้นฉบับให้ผู้เล่นเป็นคนเลือกก่อน ส่วนความเร็วที่เวลาเดินเป็นอีกเรื่องหนึ่ง นี่เป็นรูปแบบที่เหมาะกับทิศทาง Rift Ledger ที่เพิ่งแก้

## 12. เซฟในเครื่องกับออนไลน์เป็นคนละชั้น

**ตรวจโค้ด:** `src/save-store.js:1–110`, `src/cloud-sync.js:18–76`, `src/net.js:165–181`

- มีทั้ง localStorage และ IndexedDB, คิวการเขียนต่อ slot และเลือกข้อมูลใหม่ตอน hydrate
- Cloud sync ปกติทุก 5 นาที นับความสำเร็จจริง มีระยะห่างขั้นต่ำ 15 วินาทีสำหรับจุดสำคัญ และ retry 15/30/60/120/300 วินาทีเมื่อพลาด
- milestone เช่น realm/rank/บทชีวิต/ตาย/ascend กระตุ้นการส่ง มีสถานะให้ UI บอกครั้งล่าสุด/ความล้มเหลว
- พบ client เรียก API เซฟและ WebSocket; World Dungeon ใช้โมดูล `rift.js` แยกจาก solo dungeon
- ไม่ได้เห็น backend จึงยังยืนยันกฎตรวจเซฟ ความถูกต้องของคะแนนออนไลน์ หรือวิธีป้องกันโกงฝั่งเซิร์ฟเวอร์ไม่ได้
- `writeSlot` คืนค่าจาก local success หรือความพร้อมของ IndexedDB ก่อน async write จบ: ไม่ควรคัด helper นี้แล้วถือว่าเป็นหลักฐานยืนยัน durable save โดยอัตโนมัติ ต้องตรวจการรับรู้ผล async ใน caller เพิ่ม

## ระบบที่พบแต่ยังไม่ได้แกะทุกกฎ

มีโมดูลตลาด/ประมูล, ครัวเรือน/ตระกูลและที่ดิน, ตั้งสำนัก/บริหารสำนัก, ราชสำนัก/คดี/อิทธิพล, สงครามชิงบัลลังก์, campaign, Three Kingdoms, สมุดเนื้อเรื่อง/คู่มือ, audio และ pixel renderer การมีไฟล์เหล่านี้ยืนยันโครงสร้าง ไม่ได้ยืนยันว่าทุกเส้นทางสมดุลหรือไม่มีบั๊ก

## สิ่งที่ควรนำไปทำใน Rift Ledger ตามลำดับ

1. **การควบคุม:** รอผู้เล่นเลือกเป็นค่าเริ่มต้น พักเมื่อเปิดเมนู ป้องกัน touch/keyboard ที่หลุดไปเลือกด้านหลัง และให้เปิด auto แยกหมวด
2. **การตัดสินใจที่อ่านรู้เรื่อง:** แสดงสิ่งที่ต้องมี ความเสี่ยง/ช่วงโอกาส ต้นทุน และผลคาดหวัง โดยไม่เปิดเผยเนื้อเรื่องลับ
3. **แผนลงเกต:** ตั้งเป้าหมาย ความเสี่ยง และ HP ที่ควรถอย พร้อมอธิบายว่าไม่ใช่รับประกันรอด
4. **ความต่อเนื่อง:** ให้เรื่องยาวผูกกับคนจริงและการกระทำเก่า; เพื่อน/คู่แข่งมีชีวิตของตัวเอง
5. **ความน่าเชื่อถือของเซฟ:** checkpoint หลังตัดสินใจสำคัญ, แสดงผลบันทึกจริง, backup/import recovery ก่อนขยายระบบออนไลน์
6. **สูตรพลังที่ตรวจได้:** แยกแรงก์ วิชา อุปกรณ์ stat และทดสอบหลาย seed ก่อนปรับตัวเลข ไม่คัดอัตรา 1.7 หรือผลทดลองมาใช้ตรง ๆ

ไม่แนะนำเพิ่มทุกระบบพร้อมกัน Rift Ledger มีระบบจำนวนมากแล้ว ควรทำให้วงจร “เห็นเป้าหมาย → เตรียมตัว → เลือก → เห็นผล → จำผลครั้งก่อน” ชัดก่อนขยายราชสำนัก/สงครามหรือออนไลน์

## ข้อจำกัดเชิงวิศวกรรมที่เห็นจาก snapshot

`sim.js` ประมาณ 1.70 MB และ `ui.js` ประมาณ 1.03 MB; ไฟล์ content บางชุดใหญ่หลาย MB เป็นข้อสังเกตเรื่องความซับซ้อน ไม่ใช่หลักฐานว่าหน้าแรกดาวน์โหลดทั้งหมดหรือเกมช้า เพราะ HAR อาจรวม cache/service worker หลายช่วง มี error recovery ใน `advanceMonth` ที่ล้าง pending และขยับเดือนเมื่อเกิด exception ใน browser; เป็นทางหนีเกมค้างที่ควรทดสอบเรื่องผลลัพธ์สูญหาย ไม่ใช่รูปแบบที่ควรนำไปใช้โดยไม่มี logging/recovery

รอบนี้ทำ static review และทดลองเฉพาะสูตรต่อสู้ ไม่ได้เล่นทุกเส้นเรื่องหรือรัน full app จาก HAR ไม่ได้ตรวจ backend ไม่ได้ยืนยันว่า source map/import graph ครบทุกไฟล์
